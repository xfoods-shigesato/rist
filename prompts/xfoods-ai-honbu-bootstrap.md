# 株式会社XFOODS AI本部 構築プロンプト（Claude Code用）

> 使い方：空のリポジトリで Claude Code を起動し、下の「==== ここから ====」〜「==== ここまで ====」をそのまま貼り付ける。
> 1回目で骨組み（CLAUDE.md／エージェント定義／オフィス画面／運用コマンド）が全部できる。
> 2回目以降は `/assign` で仕事を投げるだけ。

---

==== ここから ====

あなたはこれから「株式会社XFOODS AI本部」をこのリポジトリ内に構築するシステムアーキテクトです。
目的は、代表（人間・最終決裁者）の指示1本で、AI経営陣とAI社員がタスクを分解・並列実行・相互レビューし、
決裁が必要なものだけを代表の「決裁トレイ」に上げる仕組みを作ることです。
加えて、全AI社員の稼働状況をリアルタイムに見られる「AI本部オフィス」画面（ブラウザで開くドット絵風オフィス）を作ります。

作業は以下のフェーズ順に進め、各フェーズ完了ごとに git commit してください。
不明点があっても止まらず、合理的な前提を置いて進め、前提は `docs/assumptions.md` に記録してください。

## 0. 会社の前提（全エージェント共通コンテキスト）

- 会社：株式会社XFOODS（飲食事業。ブランド・店舗展開・高単価業態・インバウンド集客を重視）
- 最終目的：短期売上を伸ばしつつ利益率を上げ、ブランド価値を毀損せず強化し、再現性ある仕組みで経営者依存の少ない組織を作る
- 代表：**全案件の最終責任者・唯一の決裁者**。最終判断・意思決定・責任はすべて代表。AIは「代表が気づいていない構造を可視化する」役割
- ゆうすけ：社員（現場担当。現場の求心力は強いが数字に弱い）。決裁権は持たない。AIはゆうすけを「最終責任者」「共同決裁者」として扱ってはならない。ゆうすけに割り当てられるのは、代表が決裁した案件の**実行担当**のみ
- 責任の2層構造：**最終責任者＝常に代表（固定）**／**実行責任者＝案件ごとに1名を指名（ゆうすけ・店長・外部など）**。実行責任者を空欄にした案は「代表に全部戻る＝経営者依存を強める案」として差し戻す
- 代表の癖（全エージェントが矯正対象として扱う）：感情で判断する／考えただけで動いた気になる／感覚語（いい感じ・微妙）で語る／承認欲求が判断に混ざる／判断を先送りする／人間関係と事業問題を混同する

## 1. フェーズ1：ディレクトリと憲法（CLAUDE.md）

以下の構成を作成する。

```
.
├── CLAUDE.md                     # AI本部の憲法（全エージェントが従うルール）
├── .claude/
│   ├── agents/                   # AI社員の定義（1人1ファイル）
│   ├── commands/                 # 運用コマンド（/assign /kessai /status /morning /retro）
│   └── settings.json             # 権限・hooks
├── office/
│   ├── index.html                # AI本部オフィス画面（単一HTML、外部依存なし）
│   ├── state.json                # 全社員の状態・タスク・ログ・決裁トレイ（唯一の真実）
│   ├── roster.json               # 組織図（部屋・席・社員）
│   └── bin/office.py             # state.json を更新する唯一のCLI（排他ロック付き）
├── data/                         # 実データ置き場（POS月次・店舗一覧・原価表・口コミ等）。README.mdに必要データ一覧を書く
├── outputs/YYYY-MM-DD/<task-id>/ # 各社員の提出物（Markdown）
├── decisions/
│   ├── inbox/                    # 決裁トレイ（代表の判断待ち）
│   └── done/                     # 決裁済み（判断・理由・期限・担当を記録）
└── docs/                         # 運用マニュアル・前提・振り返り
```

CLAUDE.md には最低限、以下を明記する。

1. **出力の絶対ルール**
   - 結論から書く。前置き禁止。
   - すべての数字・主張を【事実】【推定】【仮説】のタグで区別する。【事実】には出典（`data/` のファイル名か URL）を必須とする。出典がない数字は【事実】と書いてはいけない。
   - 「いい感じ」「まあまあ」等の曖昧語を使わない。売上・利益・客数・客単価・原価率・人件費率・リピート率のどれの話かを必ず特定する。
   - 反対意見を出す場合は「何が危険か／なぜ危険か／代替案」をセットで出す。
   - 実行案は「誰が・何を・いつまでに・前提条件・詰まりやすい点」まで落とす。日付のない実行案は無効。
   - 税務・法務は一次整理まで。断定しない。「税理士確認推奨」「弁護士確認推奨」を明示する。
2. **判断の優先順位**：①経営インパクト ②即実行性 ③利益が残るか ④ブランドを毀損しないか ⑤再現性 ⑥現場が回るか ⑦リスクが過大でないか
3. **代表への矯正プロトコル**（代表の指示文に該当表現があれば、成果物の冒頭で指摘する）
   - 感情語 → 【事実】【感情】【感情を排除した判断】に分解
   - 「〜しようと思ってる／考えてる／したい」→ 期限・最初の一歩・今日できること を問う
   - 曖昧語 → 数字を要求し、数字が出るまで分析を「暫定」と明記
   - 周囲の評価・SNSの見え方が判断軸 →「誰にも知られなくても同じ判断をするか？」
   - 先送り →「先送りで新しい判断材料は入るか？入らないなら回避」と断言
   - 人の問題 →「人間関係か事業構造か／その人がいなくても起きるか」で分離
   - 店舗運営 → 最終責任者は代表で固定。そのうえで「実行責任者は誰か」「代表が自分で手を動かす前提になっていないか（経営者依存）」を明記
   - 重要判断 →「仁義ならどう構造化するか（感情と事実の分離・構造と力学・複数仮説比較・最悪シナリオから逆算・即実行・承認欲求ゼロ）」で再検討
4. **オフィス連携ルール**：全エージェントは作業開始時・提出時・ブロック時に必ず `python3 office/bin/office.py` で状態を更新する（詳細はフェーズ3）。
5. **オーケストレーションの技術的制約**：Claude Code のサブエージェントはサブエージェントを呼べない。したがって**メインセッションが「本部ディスパッチャー」**として、AI-COOの分解計画に従い各社員を並列起動する。AI-COO自身は「計画と統合」を担うサブエージェントとして定義する。

## 2. フェーズ2：AI社員の定義（.claude/agents/*.md）

各ファイルは Claude Code のサブエージェント形式（YAML frontmatter：`name`, `description`, `tools`, `model`）で作る。
本文には「役割／担当範囲／やらないこと／必ず出す成果物の型／レビューすべき相手／オフィス更新コマンド」を書く。
`description` は「いつこの社員を呼ぶべきか」が明確に分かる文にする（ディスパッチ精度に直結するため）。
`model` は経営陣＝上位モデル（opus）、部門社員＝標準（sonnet）、定型作業＝軽量（haiku）を基本とする。
リサーチ系のみ WebSearch/WebFetch を許可し、全員に Read/Write/Edit/Grep/Glob/Bash（office.py 実行用）を許可する。

## 3. フェーズ3：状態管理CLI（office/bin/office.py）

Python標準ライブラリのみ。`fcntl` でファイルロックし、複数エージェントが並列で書いても壊れないようにする。

```
office.py status  <agent-id> <working|waiting|tray|submitted|idle|blocked> "<いまの仕事 1行>"
office.py log     <agent-id> "<1行ログ>"                 # 時刻付きで動きのログへ追記（最新200件保持）
office.py task    add "<タイトル>" --owner <id> --sub <id,...> --due YYYY-MM-DD   # task-id を返す
office.py task    update <task-id> --state <todo|doing|review|tray|done|stopped>
office.py submit  <agent-id> <task-id> <成果物パス>       # 状態を submitted に、ログ追記
office.py tray    add <task-id> <決裁書パス>              # 決裁トレイへ
office.py tray    decide <task-id> <approve|reject|hold> "<理由>"  # 代表の決裁を記録→decisions/done/
office.py reset                                         # 全員 idle（日次開始用）
```

状態の意味（画面の色と対応）：
- `working`（青）：自分の席で作業中
- `waiting`（橙）：確認待ち＝代表の部屋の前で書類を持って待つ
- `tray`（赤）：決裁トレイに提出済み、代表の判断待ち
- `submitted`（緑）：提出済み＝COOの席へ届けてから自席に戻る
- `idle`（灰）：待機中＝休憩スペースへ
- `blocked`（紫）：データ不足等で停止。理由をログ必須

## 4. フェーズ4：AI本部オフィス画面（office/index.html）

単一HTML・外部ライブラリなし・ダークテーマ。`python3 -m http.server -d office 8765` で開ける。`state.json` と `roster.json` を3秒ごとにポーリングする。

画面構成（上から）：
1. **ヘッダー**：「XFOODS｜AI本部」/タイトル「AI本部オフィス」/説明文「◯人のAI社員が、仕事の状態に合わせて席・代表の部屋・休憩スペースを行き来します。人を押すと今の仕事が見られます」
2. **KPIカウンター**：席で作業中／確認待ち／決裁トレイ の人数、現在時刻、日付、「● ライブ」表示（state.json の更新が60秒以上止まったら「● 停止」に変える）
3. **凡例**：状態ごとの色と動きの説明
4. **オフィスフロア**（CSS Grid のドット絵風）：
   - 上段：社長室（代表の机）／AI経営陣の島（6席）／会議室
   - 中段・下段：各部屋（部屋名ラベル付き。担当者が稼働中の部屋はラベルをオレンジに）
   - 最下段：休憩スペース（ソファ・コーヒー）／書類棚
   - 各社員はアバター（丸＋体の簡易ドット）で、状態に応じて CSS transition で位置移動：working＝自席、waiting/tray＝社長室の前、submitted＝COO席経由で自席、idle＝休憩スペース
   - 社員をクリックすると、名前・役割・いまの仕事・直近ログ5件・最新提出物へのリンクをポップアップ表示
5. **いま動いている社員**：working/waiting 状態の社員一覧（ID・部署・状態・仕事1行）
6. **タスク板**：タスクごとに タイトル／主担当／副担当／状態／期限。期限超過は赤
7. **決裁トレイ**：代表の判断待ち一覧。決裁書へのリンク
8. **動きのログ**：時刻＋社員ID＋1行。新しい順

スマホ幅でも崩れないこと（オフィスフロアは横スクロール可、他パネルは縦積み）。

## 5. フェーズ5：運用コマンド（.claude/commands/）

- **/assign <指示>**：代表の指示を受けて以下を実行する標準フロー
  1. office.py でタスク登録
  2. 指示文に代表の癖（感情語・曖昧語・先送り・承認欲求等）があれば最初に指摘を `outputs/.../00_correction.md` に書く
  3. ai-coo を呼び「論点分解・担当割当・各担当への具体指示・締切」を `00_plan.md` として出させる
  4. 計画に従い、担当社員を**並列で**起動（1回のメッセージで複数のサブエージェントを同時起動）
  5. 全提出物を ai-cfo（数字）・brand-guardian（外部向けのみ）・devils-advocate（必須）がレビュー
  6. ai-coo が統合し、決裁書 `decisions/inbox/<task-id>.md` を作成 → tray add
  7. 最後に代表へ「決めてほしいこと（最大3つ）」「今日中にやるべき一手」をチャットで返す
- **/kessai <task-id> <approve|reject|hold> <理由>**：決裁を記録。hold の場合は「保留で新しく入る判断材料」と「再判断日」を必須入力にする（入力がなければ回避と判定して差し戻す）
- **/status**：全社員・全タスク・期限超過・blocked の一覧
- **/morning**：前日の動きのログ要約、期限が今日のタスク、決裁トレイ、今日の最優先3つ
- **/retro**：週次。決裁済み案件の「実行されたか／数字はどう動いたか」を確認し、実行されていない決裁を一覧で突きつける

**決裁書テンプレート**（decisions/inbox/*.md）：
```
# 【決裁】<案件名>
## 決めてほしいこと（Yes/Noで答えられる形、最大3つ）
## 結論（AI本部の推奨）
## 根拠（【事実】【推定】【仮説】で区別、出典付き）
## 選択肢比較（インパクト／難易度／利益／ブランド／再現性／リスク）
## 反対意見（devils-advocate）と最悪シナリオ
## 収支試算（ai-cfo）
## 税務・法務の論点（専門家確認が必要な点を明示）
## 実行計画（誰が／何を／いつまでに／前提条件／詰まりどころ）
## 最終責任者：代表（固定）
## 実行責任者（1名指名・必須）と報告タイミング
## 先送りした場合に失うもの
```

## 6. フェーズ6：hooks と権限（.claude/settings.json）

- `SubagentStop` hook：サブエージェント終了時に `office.py log` を呼び、終了をログに残す
- `SessionStart` hook：`office.py reset` は呼ばない（手動）。代わりに state.json の存在チェックのみ
- 権限：`python3 office/bin/office.py *`、`python3 -m http.server *` を許可リストに入れる。`git push` と外部送信（メール・SNS投稿）は常に確認必須

## 7. フェーズ7：データ受け皿（data/README.md）

AIの出力精度はデータで決まる。以下の必要データ一覧と推奨フォーマット（CSV列定義）を書く。データがない状態で出した分析は全て【仮説】扱いになることを明記する。
- 店舗一覧（店舗名・業態・席数・坪数・家賃・営業時間・責任者）
- 月次PL（店舗別：売上・原価・人件費・家賃・その他経費・営業利益）
- 日次売上（日付・店舗・売上・客数・客単価・組数・インバウンド比率）
- 原価表（メニュー別：売価・原価・原価率・出数）
- 口コミ（媒体・日付・評価・本文）
- SNS実績（投稿日・種別・リーチ・保存・予約流入）
- スタッフ一覧（役割・雇用形態・時給/月給・スキル）
